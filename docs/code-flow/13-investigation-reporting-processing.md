## A. WHY these three modules exist

A CFO system is judged on one afternoon: someone in a dispute asks *where did this
number come from?* Everything upstream in this repository — ingestion, normalization,
the truth engine, evidence, opportunity detection — exists to produce a figure. These
three packages are where the figure is either **defended** or **lost**. An automated
money-finding platform that cannot walk a number back to the supplier's row 4,317, and
cannot hand a controller a signed-off PDF of the period, produces findings nobody acts
on; the cost is not a wrong number, it is a number no one is willing to act on. So
this slice is defensive by design: the bad outcome it prevents is a *plausible but
unattributable* financial claim, and — on the reporting side — a *plausible but
unverifiable* one.

The three packages answer three different questions, and the split is not cosmetic:

| module | question | character |
|---|---|---|
| `investigation` | *why does this number exist?* | a human workstream; a **view** over lineage, not a second source of truth |
| `reporting` | *give me the same view on paper.* | a **renderer**; it computes nothing and asserts nothing |
| `processing` | *do that again tomorrow, and do not lose work.* | batch scaffolding; its value is restartability, not speed |

**Hard invariants.** These are the promises the rest of this chapter keeps referring
back to. None is enforced by code today.

- **An investigation asserts no monetary amount.** The money belongs to the
  opportunity. A second copy of a figure inside the review record is exactly how a
  review page ends up disagreeing with the ledger, and the disagreement is discovered
  during a dispute.
- **Investigation closure is terminal and always carries a written conclusion**, so
  the audit question "was this looked at, by whom, and what was decided" has a row to
  answer it. Reopened work is a *new* investigation, so history is additive.
- **Every status transition raises exactly one audit event**, through
  `platform.audit.AuditService`. `AuditEventType` is a persisted storage contract
  (`AuditEventType.java:10-15`) — a constant cannot be renamed, only added to.
- **A report computes nothing.** Every figure on a generated PDF is a `Money` read
  from persisted truth, grouped per currency, never re-derived, never converted, never
  summed across currencies.
- **Artifact bytes never enter the database.** `ReportArtifact` is a *reference* —
  a storage key, a length, a SHA-256 checksum — pointing at
  `platform.storage.ObjectStoragePort`.
- **A job is idempotent by its run identity**, because Spring Batch will re-execute a
  chunk that already committed work.
- **An ineligible unit is `SKIPPED`, never `FAILED`.** A batch that was never eligible
  is not an error and must not page anyone.

### B.1 Raising and resolving an investigation

1. **Trigger** — a user asks for an opportunity to be investigated, through the
   opportunity module's own review boundary or through
   `investigation/controller/InvestigationController.java:9` once it carries code.
2. **Where** — `investigation/service/InvestigationService.java:9`. It resolves the
   opportunity *within the caller's organization*.
3. **What it does** — throws `NotFoundException` when the opportunity is not there.
4. **Why** — §6 of `docs/architecture/module-implementation-rules.md:103-106` forbids
   distinguishing "absent" from "belongs to someone else". Answering 403 instead of
   404 turns the endpoint into a tenant-existence oracle. Tenant scope comes from
   `SecurityContext`, never from a request body (same rule, `:102`).

5. **Trigger** — the open transition.
6. **Where** — `investigation/service/InvestigationService.java:9`; the row shape is
   `investigation/model/Investigation.java:9`.
7. **What it does** — writes the investigation and records `INVESTIGATION_OPENED`
   via `AuditService`.
8. **Why** — the opening rationale is mandatory. An investigation with no stated
   reason is a row that cannot be closed meaningfully, and it is the row a regulator
   reads first.

9. **Trigger** — assignment.
10. **Where** — `InvestigationService`, same type; status in
    `investigation/enums/InvestigationStatus.java:9`.
11. **What it does** — moves the record to its assigned state, records
    `INVESTIGATION_ASSIGNED`. No money is touched on this path.
12. **Why** — the status enum's real job is making illegal transitions
    *unrepresentable*: a sealed set with an exhaustive `switch` means adding a state
    forces every handler to be revisited at compile time (§10,
    `module-implementation-rules.md:148-149`).

13. **Trigger** — the reviewer opens the lineage view.
14. **Where** — the same service coordinates a walk across the graph owned by
    `evidence` (`LineageService`, `LineageNode`, `LineageEdge`,
    `LineageRelationType`).
15. **What it does** — traverses source file → source row → canonical record →
    calculation result → opportunity → action → outcome, returning nodes and edges.
16. **Why** — the graph is assembled per request rather than stored on the
    investigation. A cached copy is a second source of truth that goes stale the
    moment a run recomputes a figure. A node that cannot be resolved to a source row
    is reported as an **unresolved link**, never skipped: a lineage view that silently
    omits the hop it could not resolve looks complete, and "looks complete" is worse
    than no view at all.

17. **Trigger** — closure.
18. **Where** — `InvestigationService`.
19. **What it does** — requires a written conclusion, records `INVESTIGATION_CLOSED`.
20. **Why** — closure is terminal. This is not a policy preference; the schema already
    encodes it. `V8__create_opportunities.sql:187-189` makes `resolution VARCHAR(4000)`
    nullable and comments that *"NULL while open. The column existing at all is what
    allows an investigation to be closed with no finding, which is a legitimate and
    common outcome."* So "no finding" is a valid terminal state — but it must be
    *stated*, and the same comment makes `closed_at` the terminality marker.

### B.2 Generating a report

1. **Trigger** — `POST` with `reporting/dto/GenerateOpportunityReportRequest.java:9`.
2. **Where** — `reporting/controller/ReportController.java:9` → `reporting/service/ReportService.java:9`.
3. **What it does** — validates the request, creates a `Report` row in a pending
   state, and returns a report id and a status.
4. **Why** — generation is asynchronous by design. PDF rendering is CPU-bound and
   unbounded in duration; doing it on the request thread turns a 40-second period
   close into a gateway timeout with no artifact. Tenant comes from the principal,
   never the body (§6).

5. **Trigger** — the job start.
6. **Where** — `processing/reporting/ReportJobLauncher.java:9`.
7. **What it does** — supplies `JobParameters` (report type, period, tenant) and
   starts the job defined by `processing/reporting/ReportJobConfiguration.java:9`.
8. **Why** — the batch path has no request body to carry an as-of date, so the
   parameters are the *only* reproducibility handle. The same request parameters
   must select exactly the same rows a second time, or §4
   (`module-implementation-rules.md:73-85`) is violated for reports just as it is for
   the truth engine.

9. **Trigger** — content assembly.
10. **Where** — `reporting/service/OpportunityReportService.java:9`.
11. **What it does** — builds the report model from persisted truth: impacts grouped
    per currency, top opportunities, attribution summary.
12. **Why** — it aggregates stored `Money` values and never re-derives them. A total
    recomputed at render time is a total that can disagree with the ledger, and a PDF
    that disagrees with the ledger is the artefact a counterparty will quote.

13. **Trigger** — rendering.
14. **Where** — `reporting/pdf/PdfTemplateService.java:9` loads the versioned
    classpath template; `reporting/pdf/PdfReportGenerator.java:9` renders it.
15. **What it does** — produces PDF bytes with resource limits in force.
16. **Why** — see D.B for the four limits and the injection boundary.

17. **Trigger** — persistence of the bytes.
18. **Where** — `platform.storage.ObjectStoragePort.store(...)`
    (`ObjectStoragePort.java:30`); the record is `reporting/model/ReportArtifact.java:9`.
19. **What it does** — streams the bytes under a tenant-prefixed key, records the
    returned key, byte length and SHA-256.
20. **Why** — `store` takes an `InputStream`, and its Javadoc says why
    (`ObjectStoragePort.java:20-22`): *"an evidence PDF held in memory would be a
    multi-megabyte allocation per concurrent request on the ingestion path."* A
    report generator that builds a full `byte[]` and hands it over defeats the
    streaming design for every future caller.

21. **Trigger** — download.
22. **Where** — `ReportController`; the row is `reporting/model/Report.java:9`.
23. **What it does** — the response carries metadata only (`ReportResponse`); the
    bytes are a separate read that streams with `Content-Disposition` and records
    `REPORT_EXPORTED`.
24. **Why** — polling a status must never pull a multi-megabyte payload. Generation
    records `REPORT_GENERATED`; export records `REPORT_EXPORTED` — two different
    events because "we produced it" and "somebody took it away" are different
    compliance facts, and the latter is the one an investigation needs.

### B.3 A background batch run

1. **Trigger** — a scheduler, a request thread, or an operator calls a
   `*JobLauncher` with an explicit parameter set.
2. **Where** — `processing/common/JobExecutionService.java:9`.
3. **What it does** — opens a run record, moves it `PENDING` → `RUNNING`, stamps the
   `JobInstanceId`.
4. **Why** — the run record and the Spring Batch execution must be *one* unit of
   audit. A batch trace that cannot be correlated to a business row answers "it ran"
   without answering "for which tenant, over which period".

5. **Trigger** — step execution.
6. **Where** — the four job families: `processing/ingestion/**`,
   `processing/financialtruth/**`, `processing/reporting/**`.
7. **What it does** — reads a slice, processes per item, writes per chunk; each chunk
   is one transaction.
8. **Why** — see D.C. This is the single decision that makes the rest of batch
   behaviour derivable.

9. **Trigger** — a failure.
10. **Where** — `processing/common/JobFailureHandler.java:9`.
11. **What it does** — classifies it as retryable-per-item, deterministic-per-item
    (skip), or fatal-step-wide, and records the outcome.
12. **Why** — centralising the table is what stops one job from alerting on a skipped
    unit and another from retrying a poison record forever.
    `shared/enums/ProcessingStatus.java` documents the distinction the classification
    exists to protect: *"Distinguishes `SKIPPED` from `FAILED` because a batch that was
    never eligible to run is not an error and must not be alerted on as one."*

13. **Trigger** — completion.
14. **Where** — `JobExecutionService`.
15. **What it does** — `SUCCEEDED` with the result persisted; `FAILED` with the reason
    stored *separately from the status*.
16. **Why** — a status column that also carries an error string cannot be indexed or
    grouped on. Separating them is what lets a dashboard count failures by cause.

## D. DEEP DIVE

### D.A — INVESTIGATION: the workstream that resolves a flagged opportunity

**An `Investigation` record is a review, not a finding.** It points at an
opportunity, records who opened it, who owns it, why it was raised, and how it was
concluded. It carries **no amount, no calculation, and no copy of the lineage graph** —
all three exclusions are load-bearing:

- No amount, because the money belongs to the opportunity. A duplicated figure is
  duplicated *truth*, and the two copies will disagree the first time a re-run
  recomputes the engine's figure.
- No calculation, because a review that can recompute is a second truth engine with
  none of the reproducibility discipline of the first.
- No stored graph, because lineage changes under it. Caching a walk means the review
  page shows a chain that was true when the investigation opened, and nobody can tell
  from the page that it went stale.

**The lifecycle is fully determined by `AuditEventType`.** Three constants exist —
`INVESTIGATION_OPENED`, `INVESTIGATION_ASSIGNED`, `INVESTIGATION_CLOSED`
(`AuditEventType.java:83-85`) — and no others. That is the whole spec. Note *how* the
enum is meant to be read: its own Javadoc states that each constant names **a
transition, not a state** (`AuditEventType.java:21-23`), the same way
`OPPORTUNITY_ASSIGNED` and `OPPORTUNITY_REJECTED` are events while the current state
lives on the opportunity. So `InvestigationStatus` cannot be a mirror of the audit
constants — there are three events and the enum will need at least the states those
events *leave* behind, plus whatever distinguishes a not-yet-assigned investigation.
The gap between "three events" and "N states" is a real design decision that has not
been made.

**The schema already exists — and this contradicts the common assumption.** There is
no `V11` migration; the migrations stop at `V10__create_audit.sql`. But
`investigations` was created earlier, inside the opportunity migration:
`V8__create_opportunities.sql:174`, with columns `id`, `organization_id`,
`opportunity_id`, `reference VARCHAR(64)`, `status VARCHAR(32)`, `opened_by`,
`assigned_to`, `summary VARCHAR(2000)`, `resolution VARCHAR(4000)`, `opened_at`,
`closed_at`, `version`; indexes `ux_investigations_org_reference` (`:198`) and
`ix_investigations_opp (opportunity_id, status)` (`:201`).

Three schema decisions deserve their reasons spelled out, because they constrain the
service layer:

1. **`opportunity_id` is deliberately not unique** (comment at `V8:176-179`): *"an
   opportunity may be investigated more than once (a challenge reopening a rejected
   detection), and each investigation has its own reference, its own owner and its own
   resolution."* This is why closure is terminal. The design already answered the
   "how do we reopen" question: you don't reopen, you open a second one. Uniqueness on
   `opportunity_id` would have made the challenge path impossible.
2. **`reference` is unique per `(organization_id, reference)`** — tenant-scoped
   because a globally unique reference would leak one tenant's investigation count
   through another's error messages.
3. **`resolution` is nullable and `closed_at` is the terminality marker**
   (`V8:186-189`). A nullable resolution is not a modelling oversight; the comment
   says a closed investigation with no finding is "a legitimate and common outcome".
   So the *invariant* is on the pair, not the column: `closed_at IS NOT NULL` requires a
   written `resolution`, and a `resolution` with no `closed_at` is an open
   investigation. Getting this wrong in either direction is a compliance defect —
   either a closure with no stated conclusion, or a conclusion silently sitting on a
   record that still reads as open.

**`InvestigationStatus` implies more than a label.** For the enum to earn its
existence it must make the illegal transitions *unrepresentable*, per
`module-implementation-rules.md:148-149` (sealed interface + exhaustive `switch`, so
adding a state is a compile error everywhere that must handle it). It also has to be
consistent with `VARCHAR(32)` `status` and with the index `ix_investigations_opp
(opportunity_id, status)` — that index exists to serve *the open-investigations list*,
so the values that mean "still open" are a performance-relevant set, not just a
display concern.

**Tenancy applies twice.** Every read filters on the caller's organization, and a row
belonging to another tenant is reported as not-found (§6).

**Where the audit trail ends.** `INVESTIGATION_*` are the only three events this module
may raise. Findings from the walk are written back through the opportunity and value
modules — investigation does not mutate them itself (§2 forbids cross-module imports,
`module-implementation-rules.md:47-54`).

⚠ **Review 2 — the module has a table and still declares no port.**
§11 (`module-implementation-rules.md:172-174`) asks: *"Where a component would need to
read or write persisted state, declare a narrow **port interface** in your module and
leave the implementation for the persistence pass."* `investigation/repository/InvestigationRepository.java:9`
is a bare class, not a port — no interface, no methods, no domain types. So the module
has a real table (`V8:174`) and no declared way to reach it. Either the repository
becomes a port interface returning domain results, or §11's exemption for
`*/repository/` files (`:175-176`) is being relied on — but §11 lists
`*/repository/` under *leave untouched and report*, not under *no port needed*. The
two rules pull in opposite directions and the resolution is not recorded anywhere.

### D.B — REPORTING: what a report is, what an artifact is, and why bytes live in object storage

**The intended design splits the concept in two, and the split is the whole point.**

| | `Report` | `ReportArtifact` |
|---|---|---|
| **is** | a *request and its identity* — type, period, parameters, status, requester | a *stored rendering* — storage key, byte length, content type, SHA-256 |
| **answers** | "who asked for what, over which period, and can it be reproduced?" | "where are the bytes, and are they the bytes we generated?" |
| **is mutable** | yes — its status advances | no — append-only per rendering |
| **multiplicity** | one per request | many per report |

A `Report` is the *reproducibility record*. Because it carries the parameter set, the
same parameters can regenerate the document months later — which is the reporting-side
expression of §4 (`module-implementation-rules.md:73-85`). A `ReportArtifact` is the
*integrity record*: its checksum is what lets a reader verify that the PDF in their
hands is the PDF the system produced, and it is also the cheapest available
restartability mechanism (see D.C).

**Why artifact bytes belong in `ObjectStoragePort` and not in the database.** Five
reasons, in order of consequence:

1. **Size.** A period close over a large tenant produces a multi-megabyte document. A
   `BYTEA` column holding that is a row that cannot be indexed, cannot be replicated
   cheaply, and pins a page in memory for the duration of every read.
2. **The port already argued the case.** `ObjectStoragePort.store(...)` takes an
   `InputStream` and a declared length precisely so the payload is never materialised
   (`ObjectStoragePort.java:20-30`).
3. **Eviction and migration become independent.** A `Report` row can be archived, a
   template can be re-rendered, an artifact can be re-stored under a new key, without
   touching the request record — or without rewriting it.
4. **There is a precedent in the same schema.** `evidences` stores
   `storage_key VARCHAR(1024)` with `content_hash CHAR(64) NOT NULL`
   (`V7__create_evidence_lineage.sql:58,61`), and the comment at `V7:44-45` draws the
   distinction the reporting model copies: a snapshot is inline text, an artifact's
   bytes are in object storage. `ReportArtifact` is that shape again.
5. **§5 states it as a rule, not a preference**
   (`module-implementation-rules.md:87-95`): *"Never store a full source document
   inside a business entity. Store a reference and a checksum."*

⚠ **Review 3 — `reporting` has no persistence at all, and `job_instance_id` points at
a schema this repo never creates.**

- No migration creates a `reports`, `report_artifacts`, or `reports`/`job_executions`
  table. `V1`–`V10` cover `identity`, `financial`, `ingestion`, `contract`,
  `financialtruth`, `evidence`, `opportunity` (+ `investigations`), `value` and
  `platform`. `docs/code-flow/14-database-schema.md:1319-1324` already records this.
  So `Report.java:9` and `ReportArtifact.java:9` have no table behind them, and
  unlike `investigation` they have no schema to be added mechanically to.
- The two `job_instance_id BIGINT` columns that do exist — `V3:76` (`ingestion_runs`)
  and `V6:38` (`calculation_runs`) — are nullable with **no foreign key**, because
  Spring Batch's own metadata tables (`BATCH_JOB_INSTANCE` and friends) are never
  created in this repository. The link between a business run row and a batch
  execution is therefore a bare integer whose referent lives in a schema Flyway does
  not manage. `JobExecutionService` is designed to stamp exactly this value
  (`docs/explain/11-investigation-reporting-processing.md:171-173`), and the
  integrity of that stamp rests on tables this repo does not own.

**PDF generation constraints.** Rendering is the one place in the system where a
malformed or hostile input becomes a memory exhaustion, a hang, or a file written
outside the tenant's scope. Four obligations, and the reason each exists:

- **Bounded output.** A report over an unbounded opportunity set needs a page and row
  ceiling. Without one, a period containing 100k findings is a heap exhaustion in a
  batch worker rather than a paginated report. The ceiling belongs in
  `PdfReportGenerator` because that is the only component that can stop mid-render —
  a limit enforced after the fact is an OOM that already happened.
- **Bounded memory.** Font subsets must be embedded and the template must not require
  every image resident at once. The same argument `ObjectStoragePort` makes for
  uploads applies to outputs: a generator that builds a full `byte[]` defeats the
  streaming design.
- **No outbound calls while a document is open.** If the renderer can reach the
  network or a database mid-render, a slow dependency becomes an open document held
  for the duration — and a document held open while a *tenant-scoped* write is pending
  is a cross-tenant risk, not just a latency one. The assembler
  (`OpportunityReportService`) reads everything first; the generator only lays out
  what it is given.
- **Templates are ours, never the caller's.** `PdfTemplateService` loads versioned
  classpath resources under reporting's own control. **Untrusted content must never be
  interpolated into a template unescaped.** This is the concrete reason: an opportunity
  summary, a supplier name, an investigation rationale, and a file row label are all
  attacker-influenced strings that reach the renderer as template data. If the
  template language is HTML-, XML- or PDF-operator-aware, unescaped interpolation of
  any of those turns "supplier wrote `<` in column 4" into markup in a document that
  carries the company's name and a SHA-256 claiming it is authentic. Every
  template-bound string is hostile input; escaping is the default, not a per-field
  decision. A PDF that renders a supplier's literal `</text>` and drops everything
  after it is the benign failure — the dangerous one is a template language that
  reaches the filesystem or the network.

**Determinism is a reporting requirement, not just a nice-to-have.** `Report` carries
the parameters and `ReportArtifact` carries the checksum; both exist so a regenerated
report is *byte-comparable*. Anything that breaks byte-comparability breaks the
checksum's meaning: `toUpperCase()` without `Locale.ROOT`, a `LocalDate.now()` in a
footer, a `HashMap`-ordered section. §4 forbids all three on the calculation path
(`module-implementation-rules.md:81`); the report is the visible surface of that path,
so it inherits the constraint.

### D.C — PROCESSING: the two shared services and four job families

The file *shapes* answer design questions before a line of code exists. Reading the
Javadoc on the 8 SPEC files:

| question | answer encoded in the shape | why that answer |
|---|---|---|
| **What is a chunk?** | `CalculationJobConfiguration.java:17`: *"Chunk size is a transaction boundary."* | each chunk commits atomically, so a mid-invoice failure leaves whole runs either written or absent — never a run marked complete with half its lines missing. Chunk size therefore trades throughput against *how much already-finished work a single failure repeats*. |
| **How does a run identify itself?** | `CalculationJobLauncher.java:18` and `CalculationJobConfiguration.java:21`: parameters are explicit and complete; the batch path has no request body to carry an as-of date | a run with no parameters cannot be repeated, and the engine could not select contract terms deterministically. Parameters are the reproducibility handle, and the launcher is separate from the configuration precisely so *describing* a run and *deciding to run* it have different owners. |
| **Is a failure fatal?** | `CalculationProcessor.java:30`: *"Failures are per-item, not fatal."* An invoice with a missing contract price is recorded `FAILED` with a reason and the chunk continues | aborting would discard every already-computed finding behind one bad invoice. One bad invoice in a month-end run must not cost the other nine hundred. |
| **What re-runs?** | `CalculationWriter.java:29`: *"Idempotent by run id."* `CalculationJobConfiguration.java:28`: *"The job must be idempotent by run id, so a restart after a partial failure resumes rather than duplicating."* | **Spring Batch will re-execute a chunk that already committed work.** On a restart the reader re-reads the same slice; anything the writer appends blindly is appended twice. |
| **What is the unit?** | `CalculationProcessor.java:27`: *"One item is one invoice."* The engine evaluates whole snapshots | splitting an invoice across a chunk boundary would produce a total covering only part of the lines it claims. Chunk boundaries must align with the domain's atomicity, not with a round number. |
| **Where is time read?** | `CalculationProcessor.java:24`: *"The as-of date is a job parameter, never `today()`."* `:34`: the `Clock` is the engine's, not a second one | reading the system clock in the processor makes a re-run of yesterday's job select a different contract version — the §4 violation, arrived at from a different direction. Two clocks that can disagree produce a run whose timestamps describe a moment that never happened. |
| **Who owns the transaction?** | `CalculationJobConfiguration.java:25`: *"The writer, not the job, owns transaction scope. `CalculationWriter` is where per-run atomicity is enforced; this class only chooses the chunk size that drives it."* | the job is orchestration; the writer is the thing that writes. Putting atomicity in the configuration means the guarantee lives in the file that is easiest to reconfigure. |
| **May the writer fix a wrong number?** | `CalculationWriter.java:32`: *"No recomputation."* | a stored figure that looks wrong is a finding to be reported, not a number to be quietly corrected. Silent correction destroys the evidence that the engine produced it. |
| **Do nulls become zero?** | `CalculationWriter.java:25`: *"Nulls stay null."* | a missing discount on a row means *no entitlement was established*, which is not the same as *zero variance*. Collapsing them is a reporting error with a plausible-looking number. |
| **Is rejection an error?** | `IngestionProcessor.java:19`: *"a 100k-row export with three bad rows is a success with three findings, not a failure"* | rejections are expected in normal operation. Treating them as errors makes every routine import look like an incident. |
| **Is ingestion evidence or a copy?** | `IngestionWriter.java:22`: *"Evidence, not a copy of the document"* — stored with `rawPayload`, validity flag, failure reasons, keyed by 1-based `RowCoordinate` | the writer stores what was submitted and why it was refused. No monetary interpretation happens here; that belongs downstream. |
| **What is a duplicate coordinate?** | `IngestionWriter.java:22`: V3 declares `UNIQUE (source_file_id, row_number)`, so *"a duplicate coordinate is a collision to be detected rather than an overwrite"* | the writer has to decide whether a collision is a genuine re-upload or a reader bug. Overwriting silently would let a reader offset corrupt the evidence base with no trace. |
| **What is a job instance?** | `IngestionJobConfiguration.java:21`: one job instance per `IngestionRun`, with the `JobInstanceId` recorded on the run row | a run is a single auditable unit. Without the link, a failed run can only be restarted from the file, which is the only way to reprocess a large upload *without duplicating rows an earlier attempt already accepted* (the stated reason for the column at `V3:74-76`). |
| **Who may start an ingestion job?** | `IngestionJobLauncher.java:21`: *"It must refuse to launch for anything the gate did not admit."* | the launcher's position *downstream* of the security gate is the whole control. A launcher that could be called directly would be a bypass of the gate. |

**The skip / retry / fatal table** that `JobFailureHandler` is meant to own — the
reason centralising it matters is that four job families will otherwise each invent a
slightly different version:

| failure kind | example | intended response | why |
|---|---|---|---|
| per-item, transient | storage timeout on one artifact write | bounded retries with backoff, then fail that item and continue | the same work usually succeeds; aborting the chunk discards good items |
| per-item, deterministic | a template that cannot resolve one optional field | **no** retry; skip, count, continue | a retry would fail identically — it converts one failure into *N* |
| fatal, step-wide | no tenant in scope; template resource absent | stop immediately | retrying a configuration error only delays the alert, and every retry re-runs work that will fail the same way |

**`shared/enums/ProcessingStatus` exists to make the middle row expressible.** Its
`SKIPPED` constant is documented as *"Deliberately not run: the input was already
processed or was ineligible"*, and the enum's own Javadoc names the reason it is
distinct from `FAILED`. A handler that collapses the two pages a human over a
correctly-skipped unit.

**Why a job MUST be idempotent, restated as the governing rule.** Restartability is
not a feature you switch on. It is a property that the *writer* must have, because
Spring Batch's restart semantics re-deliver items from a failed chunk. There are two
mechanisms available and neither is in place: (a) compare the artifact checksum for an
existing `(report, type, period)` tuple, or (b) claim the run through a key derived from
the job parameters, in the spirit of `platform.idempotency.IdempotencyService.claim`.
Option (a) is cheaper and is what `ReportArtifact`'s checksum exists to serve; option
(b) is the general answer and is what `JobExecutionService` would own if
`IdempotencyService` proved too request-shaped to reuse. Note that
`IdempotencyService` is explicitly *not* reusable as-is: it claims a key in its own
`REQUIRES_NEW` transaction before the work runs and returns
`PROCEED`/`REPLAY`/`IN_PROGRESS` — a request-path contract, not a batch-path one.

⚠ **Review 4 — `processing/reporting` is referenced by nobody.**
`docs/code-flow/13-stub-roadmap.md:41` counts `Processing 8` = ingestion 4 +
financialtruth 4. The `processing/reporting` pair is not in that count and is
mentioned nowhere upstream of `docs/explain/11` and `docs/PROJECT-EXPLANATION.md` —
no roadmap, no chapter, no config. The two files are also the only job files in the
module with **no contract Javadoc**, while all 8 of their siblings have it. So the one
job family that bridges `reporting` to the batch infrastructure is simultaneously
absent from the inventory, undocumented, and undesigned. Either it is aspirational and
should be deleted, or it is required and needs the same spec treatment its eight peers
have. That decision is not recorded.

⚠ **Review 5 — `docs/code-flow/04-ai-reporting.md:26` names a type in the wrong
module.** It states *"Reporting: totals from FinancialImpact per currency"*. There is
no `FinancialImpact` in `reporting`. The real type is
`financialtruth/model/FinancialImpact.java:19-27`:

```java
public record FinancialImpact(
        Money totalImpact, ImpactDirection direction, CalculationConfidence confidence,
        int evaluatedLineCount, int unevaluatedLineCount, String rationale)
```

Its compact constructor rejects a null total, a null confidence, and negative line
counts — and `rationale` is the field that matters most for reporting: it states what
was *not* included. A report that prints a `FinancialImpact` without its
`unevaluatedLineCount` and `rationale` is presenting a **floor** as a total.

**How to reconcile:** the name in chapter 04 is aspirational shorthand for a
reporting-side projection; the source of the value is unambiguously
`financialtruth.model.FinancialImpact`. But per §2, `reporting` **must not import**
`financialtruth` (`module-implementation-rules.md:47-49`). So the resolution is not
"fix the import" — it is that the consumer-owned type is what a reporting-side
projection (e.g. a `reporting`-owned `CurrencyTotal`) is built from, at the integration
milestone. **Chapter 04 should be amended to say the totals come from the integration
milestone's projection of `financialtruth.model.FinancialImpact`, grouped per currency,
never re-derived** — and chapter 04's phrasing as written is unimplementable under §2.

## E. GOTCHAS — what breaks if you get it wrong

Ranked by consequence: money first, then determinism, then evidence, then
security/tenancy, then operability.

### 1. A non-idempotent job re-runs on restart and double-posts ! — **money**

- **Symptom** — a restarted month-end run produces a calculation run whose
  `variance` is roughly double, or a report set with two artifacts for the same
  period. Nothing errors; the alert fires days later as an unexplained total.
- **Cause** — the writer appends instead of upserting by run identity. The stated
  contract is `CalculationWriter.java:29` ("Idempotent by run id") and
  `CalculationJobConfiguration.java:28`; the trigger is Spring Batch re-delivering
  items from the failed chunk on restart. The same shape reaches
  `V3:74-76`, where `job_instance_id` exists *for this reason*: without it a failed
  ingestion run can only be restarted from the file, re-accepting rows an earlier
  attempt already wrote.
- **Blast radius** — money and determinism together. Every reported total downstream
  inherits the error, and because the write is *legal*, nothing in the pipeline
  objects. Detection is manual and slow.
- **Fix** — key the write on a run id derived from `(job parameters, item identity)`,
  and make the derivation stable. Upsert on that key. Additionally, treat the artifact
  checksum for `(report, type, period)` as the existence check for report writes.

### 2. A chunk too large to hold a transaction ! — **money, availability**

- **Symptom** — an import of 100k rows holds one transaction open for the whole file;
  the run times out, or the database hits a lock/undo-pressure limit and takes
  unrelated tenants' work down with it. Failures cost the entire upload.
- **Cause** — chunk size chosen for throughput rather than as a failure bound.
  `CalculationJobConfiguration.java:17` names this precisely: chunk size *"trades
  throughput against how much work a single failure repeats."*
- **Blast radius** — multi-tenancy, because one tenant's oversized upload consumes
  shared database resources; and money, because a timeout leaves a partial write with
  no marker that it is partial.
- **Fix** — size chunks so one chunk's work fits comfortably in a transaction and a
  rollback is cheap. For `IngestionJobConfiguration.java:21` the stated target is
  explicit: *"an upload with 100k rows must be persisted in chunks so a failure costs
  one chunk rather than the whole import."*

### 3. PDF generation OOM or template injection ! — **availability, security, evidence**

- **Symptom** — two variants, and both are hard to attribute. (a) A period with a
  large opportunity set exhausts the batch worker's heap; the job dies with no
  artifact and a report that is permanently `PENDING`. (b) A supplier name, opportunity
  summary, or investigation rationale containing template metacharacters renders as
  markup — dropped content, mis-laid-out pages, or a document that reaches outside its
  template.
- **Cause** — no page/row ceiling enforced in `PdfReportGenerator.java:9` (the only
  component that can stop mid-render), and/or unescaped interpolation in
  `PdfTemplateService.java:9`. Note the amplification: the same string that is inert
  in a JSON API response is *active* when bound into a template.
- **Blast radius** — security (a document carrying the company's name and a SHA-256
  that certifies it as authentic), evidence (a truncated report that *looks* complete
  and whose checksum verifies), availability (worker death, and with it every other
  job on that worker).
- **Fix** — enforce page, row and output-byte ceilings in the generator, throwing
  rather than truncating silently; embed font subsets; make no outbound call while a
  document is open; and treat every template-bound string as hostile — escape by
  default, with an explicit opt-out that has to be justified in review.

### 4. A report shows a figure that was recomputed after generation ! — **money, evidence**

- **Symptom** — a PDF circulated in month 1 and the same period queried in month 4
  disagree, and neither number is wrong. Re-running the truth engine on a corrected
  contract term changed the underlying total; the PDF is a snapshot of the old one and
  nothing records that.
- **Cause** — `Report` carrying no parameter set and no `input_checksum`, so a
  regenerated report cannot prove it evaluated the same inputs. §4 makes this a schema
  requirement, not a feature — see the identical comment on `V6:10` and
  `input_checksum CHAR(64) NOT NULL` at `V6:34`, with
  `ix_calculation_runs_checksum (organization_id, input_checksum)` at `V6:53` and the
  rule that *"two runs with the same checksum must produce the same result"*.
- **Blast radius** — money (two defensible-looking totals) and evidence (a
  retrospective reviewer cannot tell which one was current when the PDF was issued).
  This is precisely the failure §4 was written to prevent.
- **Fix** — `Report` stores the full parameter set plus the checksum of the inputs it
  read; `ReportArtifact` stores the checksum of the bytes. Regeneration with a
  *different* input checksum is a new rendering, not a repair.

### 5. An investigation status advanced without an audit record ! — **evidence, compliance**

- **Symptom** — an investigation reads `CLOSED` with a resolution, but the audit
  table has no `INVESTIGATION_CLOSED` row. The question "was this looked at, by whom,
  and what was decided" has a half-answer: the domain says yes, the trail says nothing.
- **Cause** — the transition and the audit write are two writes with no shared
  transaction boundary. §8 anticipates exactly this: *"Auditing is not a substitute for
  domain history. A state transition should also be visible in the domain's own
  lifecycle records"* (`module-implementation-rules.md:129-130`) — which is a
  requirement for the *audit* to be written, and its converse is that the domain row
  alone is not sufficient evidence.
- **Blast radius** — evidence and compliance. `AuditEventType` is a persisted storage
  contract (`AuditEventType.java:10-15`), so the trail cannot be backfilled with a new
  constant after the fact; and an unadvanced status with no record is equally bad,
  because an investigation that was worked and never opened leaves no discoverable
  trace at all.
- **Fix** — write the transition and its audit event in one transaction, and check
  `AuditService.record(...)`'s `outcome.recorded()` for the events where a missing
  record is a compliance problem (§8, `:126-128`).

## G. WIRING — where this connects

**What this module consumes: nothing yet.** A repository-wide search for imports of
`com.fintech.cfo.investigation.*`, `com.fintech.cfo.reporting.*` and
`com.fintech.cfo.processing.*` returns exactly 29 hits — the `package` declaration on
line 1 of each of the 29 files in scope, and nothing else. No file in `src/main/java`
outside these three packages references them, and no test does either.

**This is correct, and it is §2 doing its job.** `module-implementation-rules.md:47-54`
lists `investigation`, `reporting` and `processing` among the business modules a
module **must not** import, and provides the sanctioned alternative: *"Where two
modules must exchange data, the boundary is a type owned by the *consumer* or a port
interface. The wiring between them belongs to the integration milestone, not to either
module."* All three are consumers — modules that exist to read from upstream and
present it — so having no consumers today is the expected state of an unimplemented
consumer, not a defect. The corollary is that this slice being unimplemented is not
currently breaking anything.

**What is designed to consume them.** Nothing, yet. And that is the point of the
§2 split: `reporting` and `investigation` are designed to consume *upstream output*,
not to be consumed. The named upstream types are:

| consumer | upstream module | types it is designed to read |
|---|---|---|
| `reporting` | `opportunity` | `EconomicOpportunity`, `OpportunityImpact`, `OpportunityFinding`, `NextAction` |
| `reporting` | `financialtruth` | `FinancialImpact` (`financialtruth/model/FinancialImpact.java:19`), `Variance`, `CalculationRun` |
| `reporting` | `value` | `ValueAttribution`, `Outcomes` — the attribution summary |
| `investigation` | `evidence` | `LineageService`, `LineageNode`, `LineageEdge`, `LineageRelationType`, `SourceLocation`, `Evidence` |
| `investigation` | `opportunity` + `value` | the right-hand half of the walk: `OpportunityFinding`, `NextAction`, action → `Outcomes` |
| `processing/*` | `ingestion`, `financialtruth`, `reporting` | the same records, one item at a time, under `JobParameters` |

The lineage walk's shape is fixed by `evidence`, not by investigation:
`LineageRelationType` declares a `Direction` per edge, and its Javadoc states that
*"only `TOWARD_SOURCE` edges are followed when reconstructing where a figure came
from; `TOWARD_EVIDENCE` edges are followed when assembling what can be shown to a
reviewer. Keeping the two apart is why a trace cannot accidentally walk a cycle and
loop forever."* Investigation must honour that split rather than treating the graph as
undirected — an undirected traversal over a graph that permits `SUPERSEDES` and
`RECONCILED_WITH` is a loop, not a walk.

**What must happen before the wiring is real.** In dependency order:

1. **A `V11` migration** (or a `V8`-style addendum) creating the tables `reporting`
   and `processing` need: reports, report artifacts, and job-execution bookkeeping. ⚠
   Review 3 stands until this exists — and note the asymmetry with `investigation`,
   which already has a table at `V8:174` and still declares no port.
2. **Narrow port interfaces** for the persisted state each module must read and
   write, per §11:172-174. `InvestigationRepository`, plus equivalents for reports,
   artifacts and job runs. Returning domain results, not framework types. ⚠ Review 2.
3. **The Spring Batch metadata tables**, or a documented decision to run them
   separately — otherwise the two `job_instance_id BIGINT` columns
   (`V3:76`, `V6:38`) point at integers whose referent lives in a schema this
   repository does not manage.
4. **Consumer-owned types at the integration milestone** — the wiring layer, not
   these modules. ⚠ Review 5: the totals projection from
   `financialtruth.model.FinancialImpact` is a reporting-side type, built at
   integration, not an import added to `reporting`.
5. **A `ReportJobLauncher` that is actually called** — ⚠ Review 4: today the report
   batch path is designed, undocumented upstream, and unwired, and `ReportService`
   has no way to start it.
6. **The tests in section F**, before any of the above is switched on. Restartability,
   determinism and the skip/failed distinction are properties of the wiring, not of
   any single class, and none of them can be verified by compiling a stub.
